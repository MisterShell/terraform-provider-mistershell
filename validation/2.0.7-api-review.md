# MisterShell 2.0.7 compatibility review

Review date: 2026-09-11. Provider baseline: `9ff3e73` (latest published provider:
`v2.0.1`). Backend source: `57bc6482`; both the checked-in OpenAPI document and
live `/openapi.json` identify the backend as `2.0.7`.

## Findings and proposed fixes

| Finding | Impact | Resolution for 2.0.7 |
| --- | --- | --- |
| SSH fingerprint replacement requires completed resource-check evidence. The provider has no `check_task_id`, `accepted_trust_fields`, or `accepted_identity` inputs. | A raw replacement pin in `connector_data` fails with HTTP 409. Onboarding rejects worker-observed fingerprint fields with HTTP 422. Ordinary edits with omitted pins continue working. | Document the supported UI/API check-and-accept workflow and omit observed pins from HCL. Keep explicit trust/identity acceptance outside this patch release; never silently accept a replacement. |
| Documentation only required backend 2.0 and described pin preservation without a version constraint. | Users could select a backend that predates the documented collection/trust behavior. | Require backend >= 2.0.7 for this release and explain verification status becoming `unknown` after connection edits. |
| Collection controls were implemented at `9ff3e73` but absent from the published 2.0.1 release and changelog. | Users of the released provider cannot use the new `is_enabled` control. | Publish the existing implementation in 2.0.7 with an end-user changelog and a live regression test. |
| Previous SSH trust lifecycle regression used a mock server that itself preserved the pin. | Passing tests alone did not establish compatibility with the changed backend. | Add live strict/non-strict SSH coverage for proof-derived pins, initial disabled collection, connector edits, stable resource IDs, rejection of unverified replacement pins, and a clean subsequent plan. |

No removed client API paths, incompatible stable enum changes, or newly required
request fields were found in the provider's existing supported surface. Additive
backend features (including resource-check acceptance and credential usage counts)
are distinguished from regressions in existing provider workflows.

Source evidence: backend `src/features/inventory/schemas.py`,
`src/features/inventory/service.py`, `src/features/inventory/verification_evidence.py`,
`src/features/connectivity/schemas.py`, and `ui/openapi.json`.

## Validation

- Baseline `go test ./... -count=1`: passed.
- `make test-live-staged` against the configured live 2.0.7 instance: 82 top-level
  acceptance tests passed; no failures. Coverage includes onboarding, inventory,
  credentials, tags, roles, users, workers, logs/settings, session policy,
  LDAP/OIDC/SAML providers and mappings, and AI CRUD/data sources.
- Staged-suite limitations: two superseded tag tests skipped; one Windows
  credential-mismatch subtest needs a dedicated reachable Windows fixture; one
  ambiguous-resource lookup subtest is covered by unit tests instead.
- New `TestAccNetworkResource_collectionAndSSHTrust`: passed both `strict_true`
  and `strict_false` against the live backend, including cleanup verification.
- Final `go test ./... -count=1 -timeout=10m`, `go build ./...`, `go vet ./...`,
  gofmt, and `git diff --check`: passed.
- Regenerating stable enums from backend 2.0.7 produced no changes. Generated
  Registry documentation was rebuilt twice and is idempotent.
- The live tests create and remove uniquely prefixed `tfacc-` objects and use
  an isolated SSH fixture. No API keys or environment files are committed.
