## Remaining non-blocking limitations

1. SSH host-key rotation / identity acceptance (`check_task_id`, `accepted_trust_fields`, `accepted_identity`) is not exposed; users must use the UI/API check-and-accept flow (documented).
2. `app.changelog.write` is accepted by atomic `POST /roles` but rejected by the per-permission `PUT` the provider uses — a backend inconsistency; the CHANGELOG correctly tells users to drop it.
3. Backend runs `validate_persisted_connector_data` on every resource PATCH, so a legacy SSH resource with `strict_host_key=true` and no stored pin fails even name-only updates; provider-created resources since 2.0.0 always carry a pin, so this only affects imported pre-2.0 objects.
4. `is_builtin` is not exposed on the role resource/data source (additive, future).
5. `RoleCreate.permissions` atomic create is available backend-side; the provider still uses N per-permission calls (works, just non-atomic on partial failure — state is saved before permission assignment so recovery is clean).
6. Data-source `search` filters are capped at 100 characters by the backend (422 above that); pre-existing.
