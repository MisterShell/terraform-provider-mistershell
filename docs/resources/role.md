# mistershell_role (Resource)

Manages a MisterShell role. A role groups a set of permission names and an optional location scope. Permission names are validated by the backend (no static enum). The superuser permission '*.*.*' cannot be combined with other permissions or with a location scope.

## Example Usage

```terraform
# A read-only auditor role scoped to two locations.
# restricted mode requires one or more location scope roots.
resource "mistershell_role" "auditor" {
  name                = "auditor"
  description         = "Read-only access to tags and resources in EMEA"
  location_scope_mode = "restricted"

  scope_location_ids = [
    mistershell_location.emea.id,
    mistershell_location.apac.id,
  ]

  permissions = [
    "app.tags.read",
    "app.resources.read",
  ]
}

# Creating this role requires an API key whose caller is already a superuser.
# A global superuser role. The '*.*.*' permission cannot be combined with any
# other permission, and cannot be used together with scope_location_ids.
resource "mistershell_role" "superuser" {
  name                = "superuser"
  description         = "Full administrative access"
  location_scope_mode = "global"

  permissions = ["*.*.*"]
}
```

## Schema

### Required

- `name` (String) Role name (1-100 characters).

### Optional

- `description` (String) Role description (up to 500 characters).
- `location_scope_mode` (String) Location scope mode: global applies everywhere; restricted applies only beneath scope_location_ids.
- `permissions` (Set of String) Complete permission set assigned to this role. Omitting this attribute removes all grants. The backend validates names and superuser rules.
- `scope_location_ids` (Set of Number) Location scope roots. Required and non-empty when location_scope_mode is restricted; empty for global roles.

### Read-Only

- `created_at` (String) Creation timestamp.
- `id` (Number) Role ID.
- `is_builtin` (Boolean) Whether this is a built-in role.
- `updated_at` (String) Last update timestamp.

## Location scope

`location_scope_mode = "global"` requires an empty/omitted
`scope_location_ids`. `location_scope_mode = "restricted"` requires at least
one location root and applies the role beneath those subtrees. Superuser
permission `*.*.*` is global and cannot be combined with other permissions.

`permissions` manages the complete grant set. Removing the attribute revokes
all permissions; imported roles expose their current grants for review.

Permissions and scope are submitted atomically, including transitions between
global superuser and restricted roles. `is_builtin` exposes the backend role
protection metadata.

Permission names are validated by MisterShell's live registry. Use the
`mistershell_permissions` data source to enumerate names, modules, and current
role assignments.

## Backend 2.0.7 permissions and upgrades

When upgrading from backend 2.0.1, edit `permissions` in HCL to match migrated
server-side grants. Retired names otherwise cause recurring drift and HTTP 400
`Invalid permission` on apply.

| Previous permission | Use instead |
|---|---|
| `app.workers.read`, `app.proxies.read` | `app.fabric.read` |
| `app.workers.write`, `app.proxies.write` | `app.fabric.write` |
| `app.workers.delete`, `app.proxies.delete` | `app.fabric.delete` |
| `app.resources.test`, `app.resources.session`, `app.snapshots.create` | `app.resources.execute` |
| `app.ai.chat`, `app.ai.quick_assist` | `app.ai.execute` |
| `app.facts.manage` | `app.facts.write` |
| `app.changelog.write` | Remove it; use `app.changelog.delete` if deletion is required |

For example, change `permissions = ["app.workers.read", "app.resources.test"]`
to `permissions = ["app.fabric.read", "app.resources.execute"]`.

## Backend 2.0.15 permissions and upgrades

Upgrading the backend from 2.0.7 to 2.0.15 migrates stored role grants again.
Edit `permissions` in HCL to match, or the next plan shows drift and apply
either fails or silently narrows the role:

| Previous grant | After the backend upgrade | HCL change |
|---|---|---|
| `app.tasks.delete` | Removed (scheduled tasks can no longer be deleted) | Remove it; keeping it fails with HTTP 400 `Invalid permission` |
| `app.collector.read` | Split: `app.collector.read` now covers collector policy rules only; viewing collected syslog messages needs `app.collector.execute` | Add `app.collector.execute` to keep log visibility |
| `app.sensors.read` | Split: `app.sensors.read` now covers IDS rulesets, sources, rules and alert policy; viewing IDS alerts needs `app.sensors.execute` | Add `app.sensors.execute` to keep alert visibility |
| `app.fact_policies.read` | Split: `app.fact_policies.read` now covers rules and check definitions; compliance results and history need `app.fact_policies.execute` | Add `app.fact_policies.execute` to keep compliance visibility |

The backend adds the new `*.execute` grant to every role that held the matching
`*.read` grant, so existing access is preserved server-side. If HCL is not
updated, Terraform plans to remove the added grant and the role loses that
visibility on the next apply. For example, change
`permissions = ["app.collector.read", "app.tasks.delete"]` to
`permissions = ["app.collector.read", "app.collector.execute"]`.

Granting `*.*.*` requires an API key whose caller is already a superuser. The
name `admin` is reserved. Built-in roles are protected from edits and deletion;
use the role data source to read them instead of importing them as resources.

A role listed in a `mistershell_session_policy_rule`'s
`approval.approver_role_ids` cannot be deleted while that rule exists
(MisterShell >= 2.0.10), including a disabled rule or a pending approval request
naming the role. Reference the role's `id` from the rule so Terraform destroys
the rule first.

Include the applicable delete permissions in the role used by Terraform.
For example, `app.audit.write` permits log-destination changes but destruction
requires `app.audit.delete`; group-mapping destruction requires
`app.auth_providers.delete`.
