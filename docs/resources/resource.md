# mistershell_resource (Resource)

Manages a MisterShell network resource through live onboarding. Creation requires a successful connection and may take several minutes. Set engine_id for automatic discovery (SSH falls back to Generic SSH) or resource_type for exact-type discovery. external_id is discovered and may be null.

## Example Usage

```terraform
# Automatic onboarding: MisterShell connects through SSH, discovers the most
# specific installed native type, and falls back to Generic SSH when no native
# detector matches. A successful connection is required in either case.
resource "mistershell_resource" "automatic" {
  name          = "edge-router.zurich"
  engine_id     = "ssh"
  location_id   = mistershell_location.zurich.id
  credential_id = mistershell_credential.ssh_admin.id

  connector_data = {
    host = "10.0.1.1"
    port = 22
  }
}

# Exact onboarding: when resource_type is supplied, MisterShell infers the
# engine and accepts the target only if that exact detector matches.
resource "mistershell_resource" "known_ios" {
  name          = "known-ios-router.zurich"
  resource_type = "cisco_ios"
  location_id   = mistershell_location.zurich.id
  credential_id = mistershell_credential.ssh_admin.id

  connector_data = {
    host = "10.0.1.2"
    port = 22
  }
}

# Generic SSH is the exact-type special case: a successful SSH connection is
# sufficient and no native discovery is run. external_id is normally null.
resource "mistershell_resource" "generic_ssh" {
  name          = "shell-only-host.zurich"
  resource_type = "generic_ssh"
  location_id   = mistershell_location.zurich.id
  credential_id = mistershell_credential.ssh_admin.id

  connector_data = {
    host = "10.0.1.3"
    port = 22
  }
}

resource "mistershell_tag" "production" {
  name  = "production"
  color = "#e53935"
}

# tag_ids owns the complete tag set. Omit it to leave tags unmanaged; use []
# to actively keep the resource tag-free.
resource "mistershell_resource" "tagged" {
  name          = "tagged-router.zurich"
  engine_id     = "ssh"
  location_id   = mistershell_location.zurich.id
  credential_id = mistershell_credential.ssh_admin.id
  connector_data = {
    host = "10.0.1.4"
    port = 22
  }
  tag_ids = [mistershell_tag.production.id]
}

# For an existing resource, keep its Terraform address and change these two
# attributes to park it: location_id and is_enabled. Its ID is preserved.
# A newly created resource still requires successful live onboarding.
resource "mistershell_resource" "parked" {
  name          = "parked-router"
  engine_id     = "ssh"
  location_id   = mistershell_location.parking.id
  credential_id = mistershell_credential.ssh_admin.id
  is_enabled    = false # Pause automatic snapshots; manual operations remain available.

  connector_data = {
    host = "10.0.1.5"
    port = 22
  }
}

# Native SSH automation: accept a user's registered personal SSH key (My
# Account > Account Security > My SSH keys) on its own, in place of the account
# password and second authentication factor (MFA), for direct native SSH
# sessions to this resource through the MisterShell SSH gateway. The resource
# credential, session policy, recording, and audit still apply. Only resource
# types with a shell session mode accept it; MisterShell rejects it on
# generic_rdp, generic_vnc, and generic_web with HTTP 400. Requires
# MisterShell >= 2.0.15.
resource "mistershell_resource" "automation_target" {
  name                     = "ci-runner-host.zurich"
  resource_type            = "generic_ssh"
  location_id              = mistershell_location.zurich.id
  credential_id            = mistershell_credential.ssh_admin.id
  sshgw_allow_personal_key = true

  connector_data = {
    host = "10.0.1.6"
    port = 22
  }
}
```

## Onboarding modes

Core onboarding requires **MisterShell >= 2.0.7**; `sshgw_allow_personal_key`
requires MisterShell >= 2.0.15.

Creating a resource always performs a live connection test and can take several
minutes. The provider waits up to five minutes for the worker task and its
single-use discovery proof.

- Set `engine_id` without `resource_type` for automatic onboarding. MisterShell
  tries the installed type detectors in their configured order. SSH falls back to
  `generic_ssh` after a successful connection when no native type matches;
  engines without a fallback fail when nothing matches.
- Set `resource_type` for exact onboarding. The provider resolves its engine
  from MisterShell's installed type catalog, and onboarding fails unless that
  exact detector matches. `generic_ssh` is special: a successful SSH connection
  is sufficient and no native discovery is needed.
- If both are set, they must describe the same installed type/engine pair.

`external_id` is discovered by MisterShell and is read-only. It may legitimately
be null, notably for `generic_ssh`, whose transport identity is its SSH host key.
The provider never accepts a caller-supplied external identifier.

## Runtime catalogs and connector data

Resource and credential types come from the target MisterShell instance;
installed extensions may add types. The provider therefore does not
embed a closed list. Use MisterShell's `GET /api/v1/resources/types` and
`GET /api/v1/credentials/types` endpoints to inspect the current type IDs,
engine IDs, connector JSON Schemas, and compatible credential types.

The API key needs permission to read both catalogs, start discovery worker
tasks, read their status and discovery proof, create/update/delete resources,
and read/reconcile tags when `tag_ids` is managed.

## Automatic snapshot collection and parking

`is_enabled` controls automatic snapshot collection for this resource and defaults
to `true`. Set it to `false` to pause automatic collection. Manual sessions and
operations remain available, subject to their normal permissions. Creation still
requires successful live onboarding even when `is_enabled = false`.

To park an existing resource, keep its Terraform resource address, change
`location_id` to the parking location, and set `is_enabled = false`. Both fields
update in place, preserving the resource ID. To restore it, move it to the desired
location and set `is_enabled = true`.

Moving a resource to another location alone does not pause collection. Removing
it from Terraform configuration still deletes it from MisterShell on apply;
parking requires keeping the resource in configuration.

## Personal SSH key logins through the SSH gateway

`sshgw_allow_personal_key` lets a user's own SSH key, registered in MisterShell
under **My Account → Account Security → My SSH keys**, be accepted on its own in
place of the account password and the second authentication factor (MFA) when
that user opens a direct native SSH session to this resource through the
MisterShell SSH gateway, so non-interactive automation can connect. It defaults
to `false`. The account must still be active, and the resource credential,
session policy, session recording, and audit logging still apply; deleting the
key or deactivating the user ends access. Users register their keys in the
MisterShell UI; this provider does not manage personal SSH keys.

Only resource types with a shell session mode
(SSH, database, AWS, Azure, Kubernetes) accept `true`; MisterShell rejects it on
`generic_rdp`, `generic_vnc`, and `generic_web` with HTTP 400 at apply.

**Requires MisterShell >= 2.0.15.** Older backends reject any create or update
that sends this attribute with HTTP 422 and read it back as `false`. The
provider sends it only when it is `true` on create or when its value changes, so
configurations that leave it at the default keep working on older backends.

MisterShell 2.0.15 removed the earlier API-key SSH sign-in and does not carry
existing opt-ins over: after upgrading the backend, re-enable the option on each
resource that needs it (set `sshgw_allow_personal_key = true`) and have the
automation users register an SSH key.

## SSH host-key trust

Discovery connects first and returns a proof; creation consumes that proof and
stores the observed SSH host-key fingerprint on the server. No manual fingerprint
input is needed for onboarding. Do not include `host_key_fingerprint` or
`tls_fingerprint` in onboarding `connector_data`: these are worker-observed
fields and the API rejects them with HTTP 422. Terraform keeps only configured `connector_data`
in managed state, so server-added fingerprints and defaults do not cause perpetual
diffs. Readable configured fields refresh from the API and detect external
changes. Import hydrates all readable connector settings.

When an update includes `connector_data` without `host_key_fingerprint`, MisterShell
preserves the saved fingerprint. Updating another connection setting therefore
does not clear the pin or accept an observed replacement key.

`strict_host_key` defaults to `true`: runtime connections require a valid stored
fingerprint matching the presented key. With `strict_host_key = false`, a different
observed SSH key does not block connections. The stored pin remains available if
strict checking is enabled again.

Trust and identity changes require reviewed check evidence. This workflow is
verified against MisterShell 2.0.22 and requires its completed edit-check API:

1. Submit the exact draft to `POST /api/v1/resources/{id}/verify` using the same
   API principal as Terraform. Include `resource_name`, `credential_id`,
   `location_id`, and `connector_data`; omit observed fingerprints.
2. Poll `GET /api/v1/worker-tasks/{task_id}` until it completes. Review the
   verification report and the offered trust or external identity change.
3. Set `check_task_id` to that task ID alongside the matching draft. Set
   `accepted_trust_fields = ["host_key_fingerprint"]` only to accept the reviewed
   SSH key, and `accepted_identity = true` only to accept an offered identity
   change. Either acceptance is optional; there is no automatic acceptance.
4. Apply before the evidence expires. MisterShell rejects evidence belonging to
   another principal/resource, a changed draft or credential, stale evidence, or
   an acceptance not offered by the check. Obtain and review a new check after
   any such rejection.

The task ID is submitted when it changes. Keeping it in configuration does not
replay the acceptance on later metadata edits. A subsequent acceptance requires
a new task ID. These fields apply only to updates; initial creation still uses
discovery proof. `external_id` stays read-only.

## Writable metadata and health

`extra_data` is optional and computed. Omit it to read discovered metadata, or
configure an object containing the metadata/configuration keys you manage.
The installed resource type validates its schema. `file_transfer_available` is
a discovered observation and cannot be configured. On create, the provider
saves configured metadata through a follow-up PATCH after persisting the newly
created resource ID. On update, only known changed metadata is submitted.
Removing the attribute relinquishes management; use `{}` to clear writable keys.
Accepting completed check evidence can refresh discovered metadata. If that
refresh overwrites configured keys, the provider reapplies your configured
metadata after acceptance. MisterShell then marks the earlier verification as
historical because the configuration changed; the accepted identity or host key
remains saved. A later check can verify the final configuration.

| `health_status` | Meaning |
|---|---|
| `healthy` | Healthy according to the latest observation. |
| `degraded` | Degraded operation. |
| `critical` | Critical health issue. |
| `unknown` | Health has not been determined. |

`last_health_at` is the timestamp of the latest health observation. Both health
attributes are read-only and also available from the resource data source.

Changing connection settings, credentials, or location without retaining a
resource check resets the resource's status to `unknown` until a subsequent
manual or scheduled check. Historical `last_connectivity_result` evidence can
remain present with `configuration_current = false`; it does not verify the
new settings.

## Tagging

`tag_ids` is the complete tag set managed from the resource side. Omit it to
leave tags unmanaged, or set `[]` to actively clear and keep the resource free
of tags. Do not manage the same tag-resource edge simultaneously through
`mistershell_tag.resource_ids`. The computed `tags` list always reflects live
server state.
